# UQRoute-TC

Uncertainty-Gated Small-Model Routing under Deployment Perturbations

## Project Description

UQRoute-TC investigates whether uncertainty-gated routing remains reliable when small language models perform structured tool calling under realistic deployment perturbations. A tool-calling model must select the correct tool and generate valid arguments, but changes to user instructions, observations, tool descriptions, argument schemas, reward-related information, and runtime behavior can cause incorrect calls even when the model appears confident. The system will use a small model by default, accept its proposed tool call when uncertainty is sufficiently low, and escalate the original request to a stronger fallback model when uncertainty is high. The central research question is: How well do single-sample and repeated-sample uncertainty measures distinguish correct from incorrect tool calls under clean and perturbed conditions, and can uncertainty-based escalation reduce cost per successful task while preserving reliability? The study also separates pre-execution routing, where uncertainty is available before a tool is called, from post-error recovery, where transition faults such as timeouts, rate limits, server errors, or malformed responses become known only after execution.

The project will use the official RobustBench-TC release rather than constructing a new perturbation benchmark. The primary evaluation population contains 2,477 rows grouped into 199 clean-anchored base tasks, while the complete 2,527-row, 248-group population will be retained for sensitivity analysis. Qwen2.5-1.5B-Instruct, Llama-3.2-3B-Instruct, and Qwen2.5-7B-Instruct will serve as the small models, with Qwen2.5-14B-Instruct-AWQ as the fallback. A canonical parser will normalize Python, JSON, XML, ReAct, and mixed tool-call formats while preserving meaningful differences in tool names, argument names, values, and types. The study will compare single-generation token-probability measures with ten-generation canonical-call entropy and disagreement on a predefined subset. Routing thresholds will be selected using development groups and frozen before held-out testing. The proposed router will be compared with small-model-only, fallback-only, always-cascade, and matched random-routing policies. Evaluation will report task success, confident failures, calibration, AUROC, AUPRC, risk-coverage, fallback rate, latency, GPU usage, and cost per successful task, including failed attempts, repeated sampling, recovery, and fallback calls. The models will remain frozen, and the final outputs will include a reproducible routing toolkit, experiment pipeline, failure analysis, capstone report, presentation, and a workshop- or conference-ready research paper targeted for submission after the experimental results and claims are verified.

## Main Tasks

### Task 1: Reproduce the Benchmark and Freeze the Evaluation Protocol

Set up the official RobustBench-TC benchmark and scoring workflow, pin the required code and model revisions, and verify the released dataset structure. Preserve clean and perturbed versions of each task under the same base-task identifier when creating development and held-out test splits. Build a resumable experiment runner that records prompts, model outputs, scores, timing, seeds, perturbation metadata, configuration values, and file or revision hashes. Run a small pilot to validate scoring consistency, parser compatibility, runtime behavior, and available GPU feasibility before freezing the evaluation population and protocol. Output: a verified grouped dataset split, reproducible benchmark runner, pilot evidence, and frozen evaluation protocol.

### Task 2: Implement Function-Call Uncertainty and Canonical Parsing

Build a parser that converts supported Python, JSON, XML, ReAct, and mixed tool-call outputs into a consistent canonical representation while preserving meaningful differences in tool selection, argument names, values, types, and nesting. Treat parsing failure as an explicit model outcome instead of silently discarding it. Implement single-generation uncertainty measures from token probabilities, including sequence-level, average-token, maximum-token, and meaningful-token uncertainty. On a predefined subset, generate ten outputs per case and calculate canonical-call entropy and disagreement. Manually review representative outputs to validate equivalence rules and document parsing limitations. Output: a tested canonical parser, uncertainty module, repeated-sample comparison, and parser-audit record.

### Task 3: Measure Uncertainty under Deployment Perturbations

Run the selected small models on the clean and perturbed RobustBench-TC cases using the frozen experiment settings. Compare performance across the Observation, Action, Reward, and Transition perturbation classes and examine individual perturbation types as exploratory analyses. Measure tool-call and task success, AUROC, AUPRC, calibration, and risk-coverage behavior to determine how effectively each uncertainty measure separates correct from incorrect calls. Identify high-confidence failures and analyze whether particular models or perturbation categories systematically weaken the uncertainty signal. Keep all method selection on development groups and reserve the held-out test groups for final evaluation. Output: a frozen results dataset, uncertainty comparisons, risk-coverage plots, and a documented failure catalogue.

### Task 4: Evaluate Two-Stage Routing and Cost per Successful Task

Use development data to select a global uncertainty threshold that accepts a small-model call when uncertainty is sufficiently low and escalates the original request to the fallback otherwise. Freeze the threshold before evaluating held-out groups. Compare the proposed router with small-model-only, fallback-only, always-cascade, and matched random-routing policies; retain oracle thresholds only as analytical upper bounds. Evaluate pre-execution routing separately from bounded recovery after an observed transition fault. Count every model call required by each policy, including the initial small-model attempt, repeated samples when used by the policy, fallback generation, unsuccessful attempts, and recovery calls. Report task success, fallback rate, latency, token or inference usage, GPU-seconds, and cost per successful task. Output: a working two-stage router, recovery policy, baseline comparison, and success-versus-cost analysis.

### Task 5: Complete Robustness Analysis and Release the System

Test whether the main conclusions remain stable across uncertainty measures, routing thresholds, model choices, perturbation categories, and low, base, and high deployment-cost assumptions. Estimate confidence intervals and model comparisons at the base-task-group level so that related clean and perturbed variants are not treated as independent observations. Compare single-generation and repeated-generation uncertainty, evaluate alternative threshold choices, and verify that saved experiment records reproduce the principal tables and figures. Freeze the principal tables and claims before preparing a paper in a suitable workshop or conference format, then target submission to an appropriate venue if the completed evidence and submission timeline support it. Release the code, tests, configurations, Docker workflow, documentation, permitted cached outputs, and a demonstration that can rebuild the main reliability-cost results. Output: a reproducible open-source toolkit, final experimental evidence, submission-ready research paper, capstone report, and presentation. Publication acceptance will depend on external peer review and is not required for successful completion of the capstone.

## Optional Additional Task: External Validation

If the core study is complete and sufficient time and computing resources remain, evaluate a tool-specialized model or an additional compatible benchmark. Test whether a routing threshold selected under the main development conditions transfers to the external setting while using the same parser, grouped evaluation, uncertainty measures, and cost-accounting rules. This extension is optional and does not determine completion of the main project.
